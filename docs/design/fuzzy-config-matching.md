# 按偏好模糊匹配配置（构思，未实现）

> 状态：2026-11-03 可行性分析，**尚未决定是否实现**。

## 要解决的问题

现在的抢购任务对配置只有两种写法：

- **OPTIONS**：指定 addon，库存判定和下单都按它来；
- **FQN**：锁死一整套硬件组合，只有这一条有货才下单。

两种写法都要求事先知道准确的配置名。实际场景常常是「**型号一定要，配置细节不确定**」：
比如一定要 32G 内存的 KS-LE-B（27skleb01-v1），硬盘要固态、越小越好，
但具体是 2×450 NVMe 还是 2×512 NVMe、内存频率是 2400 还是 2666，事先不知道。
写死 FQN 或 OPTIONS 只要有一处对不上，任务就永远等不到货。

## 结论

可行，改动集中。做法是把「锁死一条 FQN」换成「一条挑选规则」：
下单前从这个型号当前所有能买的配置里，按偏好挑一套。现有代码已经有一半能复用。

### 为什么可行

1. **原料都已经有**。库存接口 `/dedicated/server/datacenter/availabilities` 按机房给出
   这个型号的每一条 FQN，命名规律：
   - 内存：`ram-32g-ecc-2400`、`ram-64g-noecc-2133`
   - 硬盘：`softraid-2x450nvme`、`hardraid-3x960ssd`、`hybridsoftraid-2x450nvme-1x4000sa`（混合盘有两组）

   可以拆成结构化字段：内存容量 / ECC / 频率；硬盘块数、单块容量、介质（NVMe / SSD / SATA）、
   RAID 方式、总容量。后端 `catalog.StandardizeConfig`、前端 `describeOptionCodes`
   已有类似的解析可以参考。
2. **下单链路本来就支持「先选 FQN，再从它反推配置」**：不填 OPTIONS 时，
   `purchase.go` 就是从有货的 FQN 推出 addon 段，再用 `catalog.MatchEcoOption`
   按前缀匹配目录里的完整配置名。新功能只是替换「挑哪条 FQN」这一步，
   后面的购物车、配置、结账都不动。

## 规则的组成

| 部分 | 作用 | 「32G 内存的 KS-LE-B，最小固态版本」 |
|---|---|---|
| 硬条件 | 不满足就不算 | 内存 = 32G；硬盘介质 ∈ {NVMe, SSD}（排除机械盘） |
| 偏好排序 | 满足条件的按这个先后挑 | 硬盘总容量升序 → 价格升序 |
| 价格上限 | 安全闸 | 不超过 X €/月，超过就不买 |

常用组合可以做成预设：最便宜、最大硬盘、最小固态、内存最大。

**示例**（24sk202 在 GRA 的真实库存，2026-11-03）：
32G+2×450 NVMe、32G+4×2TB SATA、64G+2×450 NVMe、64G+4×2TB SATA。
套上面的规则：内存条件留下前两套 → 排除机械盘 → 只剩 32G+2×450 NVMe。
它没货时这个机房继续等，**不会**退而买机械盘或 64G 版本。

## 每轮下单流程

1. 取该型号在任务机房的全部 FQN。
2. **去掉目录里根本不卖的组合**——这一步必须有。实例：2026-11-03 KS-5（24sk50-v1）
   库存里只有 2×4000sa 显示有货，而 IE 目录里 24sk50-v1 的硬盘选项只有
   2×2000sa / 3×4000sa / NVMe / SSD，根本不卖 2×4000sa。依据用已缓存的公共目录（按账户地区）。
3. 套硬条件，按偏好排序。
4. 取排好序后**当前有货**的第一名下单；日志、购买历史、通知里写明「按规则选中了哪一套、排第几」。
5. 第一名在加配置时仍被 OVH 拒绝，同一轮直接换下一名，不等下一轮。

## 需要处理好的点

- **有就买还是等更好的**：第一名没货、第三名有货时，默认直接买第三名（抢机讲究快）。
  可加开关：「只买前 N 名」/「必须第一名」。**待定。**
- **购物车预热**：现在预热的购物车绑定一条固定 FQN（`session.cart.fqn`）。
  改成规则后预热排名最高且目录能卖的那套；到货的是别的配置就现场重建（约多 2 秒），
  或同时预热前两名。
- **未上架型号**（强制入队，如 27skleb01-v1）：目录和库存里都还没有它，
  无法事先判断哪套能卖，只能等它出现时现场套规则。规则本身不依赖事先知道配置有哪些，
  正好适合这种场景。
- **解析不了的命名**：认不出的段不能通过有条件限制的那一项（只在没限制的项上放行），
  宁可不买也不买错。
- **自动付款安全**：模糊匹配本质上会买到没有逐字写明的配置。
  - 建任务时显示预览：按当前库存会依次挑哪几套、各多少钱；
  - 开了自动付款时建议强制填价格上限。**待定。**
- **一个任务一个机房**：规则按机房分别评估，与现有任务模型一致。

## 改动范围（估计）

- **后端**
  - 新增 FQN 解析器 + 按规则挑选的函数，插在 `purchase.go` 现在挑选 `candidates` /
    `availableFQN` 的位置；
  - 队列表加一列 JSON 规则（与 `fqn`、`options` 并存，FQN 锁定可视为最严格的规则）；
    带宽、vRack 等不出现在 FQN 里的选项照旧走 OPTIONS；
  - 单元测试：各种命名的解析、排序、硬条件、目录不卖、价格上限。
- **前端**：新建任务对话框加「按规则选配置」编辑区（硬条件、排序、价格上限、预设、实时预览）。
- **第二阶段**：同一套规则接到监控订阅的自动下单（现在监控只能按固定配置盯）。
